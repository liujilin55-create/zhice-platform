# 比赛要求分析

入口 `/?view=requirements`。必须先选择比赛与赛道，页面优先加载所选比赛的官方资料。支持直接分析可读官方正文，或上传 PDF、Word、图片作为补充/覆盖来源。页面通过 `POST /api/competition-requirements` 发送 `multipart/form-data`，服务端负责文件解析、结构化要求、学术论文检索与报告生成。

请求必须带 `{ projectId, competitionId, trackId, revision }` 绑定；结果和存储报告同时保存 `sourceId/reportId`、原文来源、核验状态及评分原句。上传始终标为上传来源，不能冒充官方核验。覆盖模式排除官方正文和评分上下文，补充模式保留两种来源身份。恢复只读取当前绑定的显式报告，禁止默认读取最新报告。换赛中断当前页面请求，迟到结果不能关联新选择。

建议通过 `/admin` 管理后台为“比赛要求分析”单独配置 DeepSeek、豆包或阿里百炼的 API、模型和提示词。`OPENAI_API_KEY`、`OPENAI_BASE_URL`、`OPENAI_MODEL` 仍作为服务端环境变量兜底；`ACADEMIC_API_URL`、`OCR_API_URL` 和 `OCR_API_KEY` 继续用于论文和 OCR 服务。未配置模型或模型分析失败时提供围绕所选比赛的本地准备框架，标注 `mode: demo`，未知提交物和时间保持为空，评分只展示已有核验原句；不套用固定示例比赛。论文服务不可用时另行标注本地参考资料。来源冲突保留为 `conflict`，不得降为普通待核验。

## 渐进展示

页面通过共享 API 客户端发送 `Accept: application/x-ndjson`，按行接收经过 Zod 校验的事件。未声明该类型的旧客户端仍得到完整 JSON 响应。事件包括 `step`、`file`、`keywords`、`papers`、`draft`、`warning`、`heartbeat`、`complete` 和 `error`；只有 `complete` 表示最终报告通过结构校验。正常结束却没有 `complete` 视为中断。

进度包含接收文件、提取原文、提炼关键词、检索论文、解读比赛、推荐选题、设计路线、对齐评分、安排备赛、校验结果、建立溯源 11 个阶段。步骤由后台实际处理和模型已返回的字段推进，计时器只显示已用时间。文件、关键词与论文先展示；一次 `streamText + Output.object` 调用逐步产出比赛要求与指导内容，不通过额外模型调用或延时增加等待。

生成过程中的内容标注为待校验草稿，最终完成后使用正式结果替换，并启用原有导出和证据链接。未配置模型、无可读原文或模型失败时，明确展示演示标识；`draft.reset` 清除失败模型的旧内容，避免混入模板。学术服务不可用时标注本地参考资料。溯源保存失败仍提供可读报告，并提示尚未建立证据关联。

支持取消、失败保留已有内容和重新分析。客户端取消或离开模块会中止请求；服务端将取消信号传递给模型、OCR 和论文检索。PDF / DOCX 本地解析完成后检查取消信号，已进入持久化的保存操作可能已落地。服务端在 110 秒超时后结束本次分析，8 秒连接心跳不推进进度。生成期间锁定输入，重试时清空上一份草稿，旧请求不能覆盖新结果。

`node --test tests/analysis-stream.test.mjs tests/analysis-route.test.mjs` 验证碎片化 UTF-8、部分结构、事件顺序、取消、失败替换、截断流及真实 AI SDK 流协议。路由集成测试使用内存 Word 文件、模拟模型与模拟持久化，不读取真实密钥、不调用收费服务、不写用户证据库。
